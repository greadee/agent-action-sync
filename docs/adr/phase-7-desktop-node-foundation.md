# Phase 7: Desktop Node Packaging and Lifecycle

Status: accepted

## Context

The existing daemon can own SQLite, synchronization runtimes, and a loopback
administration API, but it previously ran only from a source checkout with a
hand-authored configuration. A desktop release needs an installation boundary
that cannot accidentally make application upgrades or uninstall destructive to
authority-local history or project workspaces.

## Decision

### Ship a signed, per-user Windows installer

Windows x64 releases use an Inno Setup installer under
`installer/windows/SyncGate.iss`. The application is installed below
`%LOCALAPPDATA%\Programs\SyncGate` without administrator privileges. Release
builds must Authenticode-sign both `syncgate.exe` and the compiled installer and
must timestamp both signatures. `tools/build_windows_release.ps1` fails closed
when no certificate thumbprint is supplied; unsigned artifacts require the
explicit `-AllowUnsignedDevelopment` switch and are not release artifacts.

Every artifact set includes `version-manifest.json` generated by the compiled
binary. It identifies the semantic application version, source commit, build
time, release channel, target, current control-layout version, and oldest
compatible control-layout version.

### Keep mutable roots outside the installation directory

The first-run initializer creates these per-user roots:

| Purpose | Default Windows location | Uninstall behavior |
| --- | --- | --- |
| Configuration | `%APPDATA%\SyncGate\config.json` | preserve |
| SQLite/control state | `%LOCALAPPDATA%\SyncGate\data` | preserve |
| Logs | `%LOCALAPPDATA%\SyncGate\logs` | preserve |
| Runtime cache | `%LOCALAPPDATA%\SyncGate\cache` | preserve |
| Git worktrees | `%LOCALAPPDATA%\SyncGate\worktrees` | preserve |
| Registered projects | operator-selected external roots | preserve |

The generated configuration records the mutable roots and permits zero shares,
so a new node can start safely before an operator registers a project. Existing
configuration is validated but never overwritten by initialization or upgrade.

### Use a foreground, per-user lifecycle in the first desktop release

The first desktop release is not a Windows service. `syncgate node-run` owns the
daemon in the invoking user session, prints foreground diagnostics, observes
console termination, and shuts down through the existing ordered daemon
lifecycle. This avoids a privileged service account, session-crossing credential
access, and unclear ownership of per-user Git/provider credentials. The
installer offers an explicit post-install start action but does not silently
register machine startup persistence.

A service or tray-process design requires a later ADR covering user-session
identity, update coordination, process supervision, and UI ownership.

### Make first run and compatibility checks explicit

`syncgate node-init` creates the separated directories, an empty production
configuration, and `desktop-control-state.json`. The operation is idempotent.
`syncgate node-run` repeats the compatibility check before opening SQLite.

The state contains an integer control-layout version. A binary refuses startup
when state is newer than its supported maximum or older than its declared
minimum. Installer semantic-version downgrades are blocked by default and
require `/ALLOWDOWNGRADE=1`; the binary compatibility check still has final
authority. SQLite migrations remain forward-only and no downgrade performs a
schema rollback.

### Keep health local and bounded

The existing unauthenticated `GET /healthz` route remains loopback-only and
returns only `{"status":"ok"}` when the daemon is ready. `syncgate node-health`
uses a proxy-free, timeout-bounded loopback client and rejects non-loopback
targets. Authenticated status and diagnostic routes remain separate.

### Preserve state on uninstall

The installer deliberately has no uninstall deletion rules for mutable roots.
Uninstall removes application files and shortcuts only. Deleting configuration,
control state, projects, or worktrees is a distinct manual operator action.

## Consequences

- Fresh installs can become healthy before project registration.
- Application replacement and uninstall cannot remove the SQLite control store
  or Git worktrees through installer ownership.
- Downgrades fail closed at both installer version and binary layout boundaries.
- The initial lifecycle is intentionally per-user and foreground; automatic
  background startup is deferred.
- Producing a public release requires a managed code-signing certificate and a
  clean Windows packaging host.
